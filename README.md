# Mangal House

**Mangal House** — клиент-серверное приложение для заказа блюд ресторана: мобильный и веб-клиент на React Native / Expo, REST API на Express, PostgreSQL и административная панель AdminJS.

Проект включает клиентское приложение, серверную бизнес-логику, PostgreSQL-базу данных и инструменты управления меню и заказами. Основной сценарий: пользователь выбирает блюда → добавляет их в корзину → указывает адрес → оформляет заказ → просматривает его статус и историю в профиле.

> **Статус:** проект находится в активной разработке (MVP). Регистрация, каталог, корзина, оформление заказа, профиль и адреса проверялись локально. Платежи, push-уведомления и live-отслеживание доставки пока не реализованы.

## Что реализовано

### Клиентское приложение

- **Авторизация:** регистрация, вход по номеру телефона и паролю, JWT-сессия, выход из аккаунта.
- **Главная:** витрина блюд, категории, популярные позиции, переход к подробной карточке.
- **Каталог:** поиск по названию и описанию, фильтры по категориям/наличию/популярности, сортировка по цене.
- **Карточка блюда:** описание, фото (при наличии), стоимость, выбор количества и добавление в корзину.
- **Корзина:** изменение количества, удаление позиций, подсчёт стоимости и оформление заказа.
- **Профиль:** имя, телефон, адрес, история заказов с деталями и текущими статусами.
- **Редактирование профиля:** обновление имени и основного адреса доставки через защищённый API.
- **Адресная книга:** несколько адресов с произвольными названиями, выбор основного, удаление адресов.
- **Единая тема:** цвета интерфейса управляются через `constants/palette.json` и `constants/brand.ts`.

### Backend и административная часть

- REST API для пользователей, меню и заказов.
- PostgreSQL + Sequelize ORM, миграции и демонстрационный сидер меню.
- Пароли пользователей хранятся в виде bcrypt-хешей; защищённые пользовательские маршруты используют JWT.
- При оформлении заказа сервер проверяет доступность блюд и **сам рассчитывает сумму** на основе актуальных цен в БД. Состав заказа сохраняется как снимок позиций с ценами и количеством.
- Заказы привязаны к аккаунту: пользователь получает только собственную историю.
- **AdminJS** по адресу `/admin` — управление записями меню и заказами.
- Административные REST-маршруты защищены отдельным заголовком `x-admin-api-key`.
- Статусы заказа: `new`, `cooking`, `delivering`, `completed`, `cancelled`.

## Локальный запуск

### Требования

- Node.js и npm (рекомендуется актуальная LTS-версия Node.js).
- PostgreSQL с доступной локальной БД.
- Android Studio с эмулятором, либо устройство с Expo Go; для Web — браузер.

### 1. Установить зависимости

Из корня репозитория:

```bash
npm ci
cd backend
npm ci
```

### 2. Настроить backend

Скопировать `backend/.env.example` в `backend/.env` и указать собственные значения:

```dotenv
DB_HOST=localhost
DB_PORT=5432
DB_NAME=mangal_house
DB_USER=postgres
DB_PASSWORD=YOUR_DB_PASSWORD

PORT=5000
JWT_SECRET=YOUR_LONG_RANDOM_JWT_SECRET
ADMIN_API_KEY=YOUR_RANDOM_ADMIN_API_KEY
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=YOUR_ADMIN_PASSWORD
ADMIN_COOKIE_SECRET=YOUR_RANDOM_SECRET_AT_LEAST_32_CHARS
```

Создать в PostgreSQL базу `mangal_house` (или указать имя уже существующей базы). Затем из папки `backend` выполнить:

```bash
npm run db:migrate
npm run db:seed
```

`db:seed` необязателен: он добавляет демонстрационные позиции меню. Повторный запуск сидера на заполненной БД может создать дубликаты; используйте его для первоначального наполнения.

> **Важно:** API-клиент по умолчанию ожидает backend на порту **5000**. В старом `.env.example` может быть указан `PORT=3000` — для стандартного запуска этого проекта замените его на `5000`.

### 3. Запустить сервер

Находясь в `backend`:

```bash
npm run dev
```

При успешном соединении с БД API доступен по `http://localhost:5000`, а админ-панель — по `http://localhost:5000/admin`.

### 4. Запустить клиент

Открыть **второй терминал** в корне репозитория:

```bash
npx expo start -c
```

- `a` — открыть Android-эмулятор.
- `w` — открыть Web-версию.
- `npm run android` / `npm run web` — альтернативные команды запуска.

**Настройка адреса API:** `services/api.ts` определяет адрес сервера в зависимости от платформы:

- **Web:** `http://localhost:5000`.
- **Android Emulator:** `http://10.0.2.2:5000` (специальный адрес хоста эмулятора).
- **Физический Android / iOS:** нужно указать локальный IP компьютера в `services/api.ts` и убедиться, что устройство и компьютер находятся в одной сети. Для физического Android также следует отключить режим `ANDROID_USE_EMULATOR`.

## Основные API-маршруты

Базовый префикс — `/api`. Формат запросов и ответов — JSON.

| Метод | Маршрут | Назначение | Доступ |
| --- | --- | --- | --- |
| `POST` | `/auth/register` | Регистрация | Публичный |
| `POST` | `/auth/login` | Авторизация, выдача JWT | Публичный |
| `GET` | `/auth/me` | Данные текущего пользователя | Bearer JWT |
| `PATCH` | `/auth/me` | Изменение имени и основного адреса | Bearer JWT |
| `GET` | `/menu` | Список блюд | Публичный |
| `GET` | `/menu/:id` | Информация о блюде | Публичный |
| `POST` | `/orders` | Оформление заказа | Bearer JWT |
| `GET` | `/orders/my` | История заказов пользователя | Bearer JWT |
| `GET` | `/orders` | Все заказы | Admin API key |
| `GET` | `/orders/:id` | Заказ по ID | Admin API key |
| `PUT` | `/orders/:id/status` | Изменение статуса | Admin API key |

Пример оформления заказа:

```http
POST /api/orders
Authorization: Bearer <JWT>
Content-Type: application/json
```

```json
{
  "customerAddress": "Воронеж, ул. Примерная, 10",
  "items": [
    { "id": 1, "quantity": 2 },
    { "id": 4, "quantity": 1 }
  ]
}
```

Клиент **не передаёт итоговую стоимость**: backend получает цены из базы, проверяет доступность блюд и формирует заказ.

## Данные и хранение

- **PostgreSQL:** пользователи, позиции меню, заказы, статусы, основной адрес пользователя.
- **AsyncStorage:** JWT и кеш профиля (`@authToken`, `@user`), корзина (`@mangal_cart_v2`), дополнительные сохранённые адреса с ключом вида `@mangal_addresses_<userId>`.
- **Адресная книга:** дополнительные адреса привязаны к аккаунту **на конкретном устройстве**. Выбранный основной адрес сохраняется через `PATCH /api/auth/me` в PostgreSQL. Полноценной синхронизации всех адресов между устройствами пока нет.
- **Изображения:** API отдаёт локальные файлы по пути `/uploads` и ссылки на изображения в данных меню.

## Основные технические решения

1. **Разделение ответственности:** `app/` отвечает за маршруты и экраны, `services/` — за взаимодействие с данными, `contexts/` — за общее состояние, а backend — за бизнес-логику и доступ к БД.
2. **Единый HTTP-клиент:** Axios в `services/api.ts` добавляет Bearer-токен к запросам автоматически.
3. **Проверка заказа на сервере:** цена и доступность не доверяются данным из клиента; заказ хранит снимок выбранных блюд.
4. **Общие токены дизайна:** палитра вынесена в `constants/palette.json`, а компоненты получают значения через `BRAND`.
5. **История заказов:** связана с авторизованным пользователем, а не с произвольным ID, переданным клиентом.

## Ограничения и ближайшие задачи

- Синхронизация всей адресной книги с backend и поддержка нескольких устройств.
- Обновление статуса заказа без ручного перезапроса (polling, WebSocket или push).
- Подтверждение и восстановление доступа к аккаунту, усиление проверок безопасности.
- Валидация полей и предельных значений на стороне сервера, централизованная обработка ошибок.
- Автоматизированные тесты API и ключевых сценариев оформления заказа.
- Подготовка отдельной production-конфигурации, HTTPS, секретов, CORS и деплоя.
- Оплата онлайн и взаимодействие со службой доставки — отдельные будущие этапы.

> `docker-compose.yml` в репозитории — **черновая конфигурация разработки**. Перед использованием необходимо согласовать в ней переменные окружения, название базы и секреты с настройками backend. Не используйте содержащиеся в примере учётные данные в production.

## Работа с репозиторием

Перед коммитом проверяйте `git status` и убедитесь, что в индекс не попали `.env`, пароли, токены, `node_modules` или другие локальные данные. **Проверьте, что `backend/.env` добавлен в `.gitignore`**: в исходной конфигурации проекта исключения только для `.env*.local` недостаточно. Для новых возможностей предпочтительны небольшие коммиты с понятным назначением (`feat:`, `fix:`, `refactor:`, `docs:`).
